# 1. 왜 서버가 반드시 필요한가

```
❌ Flutter 앱에 OpenAI 키 넣기   →  디컴파일로 털림
⭕ 앱 → 우리 서버 → OpenAI        →  키는 서버 .env 에만
```

사진에서 재료를 추정하는 호출이 이 경로를 탄다. **이것이 서버가 선택이 아니라 필수인 이유.**

부수적으로:
- 패턴 분석("4번 중 3번"), 감쇠 곡선, 등급 판정 = **전부 서버 코드**. 앱은 그리기만. 로직 바뀔 때 앱 재배포 불필요
- 사진 저장

# 2. Flutter가 백엔드에 미치는 영향

**없음.** HTTP/JSON을 주고받으면 서버 언어는 무관.

다만 세 가지가 달라짐:

| | 내용 |
|---|---|
| **"언어 통일" 이점 소멸** | RN이면 앱·서버 둘 다 JS. Flutter는 Dart라 어차피 2개 언어 → **Node를 고집할 이유 없음** |
| Firebase 궁합 | Google이 둘 다 만들어 연결이 쉬움. **단 우리는 사용 불가** |
| Dart 백엔드 | Serverpod·Dart Frog 존재. **2주엔 비추** — 자료 적어 막히면 못 풂 |

**결론: 팀이 제일 잘하는 언어로 간다.**

# 3. OpenAI 설정

## 3.1 API 키

- 조직: **중앙해커톤**
- 프로젝트: Default project
- **Owned by: You** ← 2주짜리라 이걸로 충분. 조직 이탈 시 키 비활성화되지만 상관없음

## 3.2 키 생성 시 권장 설정

| 항목 | 권장 | 이유 |
|---|---|---|
| Permissions | **Restricted** → Model capabilities만 Write | `All`은 조직 설정·결제까지 접근 가능. 서버 키에는 과함 |
| 이름 | `moru-backend-dev` 같이 구체적으로 | 나중에 어느 게 뭔지 몰라 못 지움 |

## 3.3 ⚠️ 사용량 한도 — 반드시 설정

**Settings → Billing → Limits**

```
개발 단계   $5~10 정도로 낮게
알림        80% 도달 시 이메일
```

**비전(이미지) 호출은 텍스트보다 훨씬 비싸다.** 루프 한 번 잘못 돌면 지원 크레딧을 하루에 태울 수 있음. 조직 크레딧이라 더 위험.

## 3.4 크레딧 잔액 확인 위치

```
Settings → Organization → Billing
platform.openai.com/settings/organization/billing/overview
```

| 지표 | 위치 | 뜻 |
|---|---|---|
| **Credit balance** | Settings → Billing | 남은 크레딧 |
| Spend | Home / Usage | 쓴 금액 |

⚠️ 조직에서 역할이 **Member면 Billing이 안 보일 수 있음.** Owner에게 문의.

## 3.5 키 관리 3원칙

```
1. .env 에만 둔다              →  코드 하드코딩 금지
2. .gitignore 에 .env          →  깃허브 올라가면 몇 분 내 봇이 훔쳐감
3. Flutter 앱엔 절대 안 넣는다  →  반드시 서버 경유
```

# 4. 가비아 서버

## 4.1 상품 확인이 먼저

| 보이는 메뉴 | 상품 | 판정 |
|---|---|---|
| 클라우드 서버 / g클라우드 | VPS | ✅ 우리가 원하는 것 |
| 웹호스팅 | 공유호스팅 | ⚠️ SSH 안 될 수 있음. 계획 재수립 필요 |

**경로**: 가비아 로그인 → 우측 상단 `My가비아` → 서비스 관리
클라우드 서버는 별도 콘솔로 넘어가는 경우가 많음 (`cloud.gabia.com` 계열)

## 4.2 찾아야 할 정보 4개

```
공인 IP        예) 211.xxx.xxx.xxx
접속 계정      보통 root 또는 ubuntu
SSH 포트       기본 22 (가비아가 바꿔둔 경우 있음)
OS             Ubuntu / CentOS / Rocky
```

## 4.3 생성 시 선택한/할 옵션

| 항목 | 결정 | 이유 |
|---|---|---|
| **OS** | **Ubuntu 22.04 LTS** 권장 | 자료가 제일 많음. CentOS 계열은 검색 결과가 안 맞아 시간 낭비 |
| 사양 | 1~2 vCPU / 2GB RAM | 2주 프로토타입엔 충분 |
| **스토리지** | **루트 100GB 단일** | 분리(50+50)할 이유 없음. 2주 뒤 끝나고 재설치 안 하며 사진도 몇백 장 수준. 나누면 마운트 신경 쓸 게 늘어남 |
| **로그인 방식** | **SSH 키페어** | 22번 포트는 봇이 24시간 무차별 대입. 키페어면 파일 없이는 시도 자체가 무의미 |

## 4.4 키페어 관리

- **생성 시 1회만 다운로드 가능.** 놓치면 콘솔에서 재발급
- 팀 비공개 채널로 전달 (공개 채널 절대 금지)
- **`.pem`은 깃허브 금지** — `.gitignore`에 이미 추가함

**접속**
```bash
ssh -i "경로/키.pem" 계정명@서버IP
# 포트가 22가 아니면
ssh -i "경로/키.pem" -p 포트 계정명@서버IP
```

**Windows 권한 오류 시**
```bash
icacls "키.pem" /inheritance:r
icacls "키.pem" /grant:r "%username%":R
```

## 4.5 누가 키페어를 가져야 하나

```
SSH로 서버에 들어가는 사람 (nginx·DB·배포·로그)  →  필요 ✅
Flutter 앱 개발자 (서버 IP만 알면 됨)            →  불필요
```

**"서버 기계 자체를 만지느냐"가 기준.** 앱이 API를 부르는 건 그냥 인터넷 요청이라 열쇠가 필요 없음.

백엔드가 여러 명이면 2주 기준 **`.pem` 하나를 공유**하면 충분. (각자 키를 `authorized_keys`에 추가하는 방식은 운영 단계에서)

# 5. 서버 1일차 세팅 체크리스트

**이걸 못 끝내면 나머지가 다 밀린다.**

```
□ SSH 접속
□ 런타임 설치 (Node 또는 Python)
□ DB 설치 + 계정 생성 (PostgreSQL 또는 MySQL)
□ nginx 설치 (리버스 프록시)
□ 방화벽 80 / 443 열기      ← ⚠️ 가비아 콘솔에서도 따로 열어야 함
□ 도메인 연결 (A 레코드)
□ HTTPS 인증서 (certbot 무료)   ← iOS는 http 차단이라 필수
□ pm2 또는 systemd 로 프로세스 유지
```

## 5.1 ⚠️ HTTPS는 선택이 아니다

**iOS는 ATS 때문에 평문 http를 기본 차단.** 인증서 없으면 앱이 서버와 아예 통신 못 함.
가비아는 도메인·인증서를 같이 파니 이건 오히려 편함. 무료로는 Let's Encrypt(certbot).

## 5.2 예상 함정 3개

| 함정 | 대응 |
|---|---|
| **가비아 방화벽 이중 구조** | VPS 안 `ufw`만 열어도 안 되고 **가비아 콘솔 방화벽/보안그룹**에서도 열어야 함. 여기서 반나절 날리는 팀 많음 |
| **발표 중 서버 다운** | **로컬 목데이터로 도는 폴백 모드**를 앱에 넣고 스위치 하나로 전환되게 |
| **사진 업로드 용량** | Flutter 원본은 3~5MB. **긴 변 1024px로 리사이즈해서 업로드** → 200~400KB. 안 그러면 업로드도 느리고 디스크도 빨리 참 |

# 9. 챗봇 하네스 설계

⚠️ **`spec-03 §6.3` 의 "자유 상담 챗봇 영구 금지"를 뒤집는 결정.** 챗봇을 넣되 의학적 진단이 구조적으로 불가능하게 설계한다.

## 9.1 왜 필터만으론 안 되나

```
금지어 필터:  "IBS" 차단 → "과민성 대장" 우회
              "진단" 차단 → "제 증상이 뭘까요" 우회
```
표현은 무한하고 필터는 유한하다. **답변을 검열하는 게 아니라 애초에 물어보지 못하게** 해야 한다.

## 9.2 3층 구조

**1층 · LLM에 보내기 전에 거른다**
```
레드플래그 키워드 (혈변·피·검은 변·체중 감소·발열·구토)
   → 즉시 병원 안내. LLM 호출 자체를 안 함
질문 유형 분류 (기록조회 / 음식질문 / 의료질문 / 기타)
   → 의료질문이면 정해진 문구 반환. LLM 안 감
```

**2층 · LLM이 아는 것을 제한한다**
```
❌ 일반 의학 지식으로 답변        → 진단이 나옴
⭕ 사용자 기록 + 우리 계산 결과만  → 진단이 구조적으로 불가능
```
시스템 프롬프트에 "주어진 기록에 없는 것은 모른다고 답하라"를 강제.

**3층 · 출력을 검증한다**
```
구조화 출력 강제 (자유 텍스트 금지)
금지 패턴 검사 (질병명·약물명·"~입니다" 단정·"~하세요" 명령형)
실패 시 재시도 (LLM에게 에러를 되먹여 교정)
2회 실패 시 폴백 ("정확한 건 의료진께 여쭤보시는 게 좋겠어요")
```

## 9.3 남는 위험 — 정직하게

| 위험 | 대응 |
|---|---|
| 분류기 오류 ("요즘 계속 아픈데 왜 그럴까요?"가 애매) | 확신 없으면 무조건 병원 안내로 폴백 |
| 경계가 흐린 질문 ("양파 먹어도 될까요" vs "약 먹어도 될까요") | 보수적 기본값 |
| 우회 표현 | 모든 대화 로깅 → 사후 검토 |

**공통 원칙: 애매하면 무조건 보수적으로.**

## 9.4 Python이 유리한 이유

| 하네스 층 | Python |
|---|---|
| 1층 분류 | 분류 호출도 Pydantic 스키마로 고정 |
| 3층 출력 검증 + 재시도 | `instructor` 가 자동 교정 루프 기본 제공 |
| 앱 요청 검증 | **같은 Pydantic 재사용** |

검증·재시도를 세 군데(앱 요청 / 분류 / 최종 응답)에서 쓰는데 도구가 하나로 통일된다.

## 1. 토스 (Toss) — 한글 조판

### 타이포 원칙

#### (a) TDS 타이포그래피 토큰 — 실측 수치 (출처 있음)
토스 미니앱용 공식 문서 `TDS React Native > Foundation > Typography`에 공개된 토큰 표입니다. **fontSize / lineHeight만 공개**되어 있고 letterSpacing 값은 문서에 명시되어 있지 않습니다.

| subTypography 1 | 29 | 38 | 1.310 |
| subTypography 2 | 28 | 37 | 1.321 |
| subTypography 3 | 27 | 36 | 1.333 |
| Typography 2 | 26 | 35 | 1.346 |
| subTypography 4 | 25 | 34 | 1.360 |
| subTypography 5 | 24 | 33 | 1.375 |
| subTypography 6 | 23 | 32 | 1.391 |
| Typography 3 | 22 | 31 | 1.409 |
| subTypography 7 | 21 | 30 | 1.428 |

각 토큰은 Light / Regular / Medium / Semibold / Bold 5개 웨이트를 가집니다.

**여기서 읽어낼 수 있는 규칙 (수치 기반, 추측 아님)**
- **18px 이하는 행간이 정확히 1.5배로 고정**됨. 본문 영역 전체가 1.5.
- **19px 이상부터 행간 배수가 점점 줄어듦** (제목이 커질수록 1.5 → 1.33까지 조여짐).
- 즉 토스의 한글 조판 룰은 "**본문 1.5 고정 / 제목은 크기가 커질수록 행간 배수를 줄인다**"로 요약됨.
- 스텝이 1px 단위로 촘촘함 (11~30px 전 구간). 큰 점프를 두지 않음.

#### (b) 자간(letter-spacing)
- **확인 실패.** TDS 공식 문서에 letterSpacing 토큰 값이 공개되어 있지 않고, 토스가 자간 수치를 명시한 공개 아티클도 찾지 못했습니다.
- 한글 UI 일반론으로 "16~17pt 본문에 약 -0.3 정도 자간을 좁힌다"는 서술은 있으나 **토스 출처가 아니므로 토스 기준으로 인용하면 안 됨**.

#### (c) 토스 프로덕트 산스 (Toss Product Sans) — 공개된 제작 원칙
토스피드 「토스 프로덕트 산스 제작기」 원문에서 확인된 내용:

- 배경: "환경마다 다른 서체를 쓰면서 비효율적인 상황이 발생했고, 가독성과 사용성이 가장 뛰어난 토스만의 본문용 서체가 필요해졌어요." (iOS는 San Francisco, 윈도우는 맑은 고딕을 쓰던 상황)
- 제작: 2020년 여름부터 산돌과 협업, 7개월간 14번 협의 → 1차 버전. 이후 이도타입과 개선. (기사 시점 3차 버전 제작 중)
- **숫자·영문을 한글보다 두껍게**: "일반적으로 본문용 서체의 숫자와 영문은 국문보다 조금 더 작은 크기로 디자인되어 있어요" → 디지털 환경에 맞춰 숫자·영문을 국문보다 더 두껍게 설계. (완전히 동일 두께로 맞추면 숫자·영문이 얇아 보임)
- **기호를 아이콘처럼**: "퍼센트, 쉼표, 더하기, 빼기, 화살표 등 가장 많이 사용되면서 UI 요소로 활용되는 기호들의 가독성을 높였습니다. 더 크게, 아이콘에 가깝게 좀 더 넓은 여백으로 디자인했죠."
- **흰 공간 관리**: 점과 글자 사이, 기호 간격, 중앙선 두께를 정밀 조정. "띄어쓰기 간격까지도 신경 썼고요."
- **고정폭/가변폭 숫자 분리**: "프로덕트 산스는 가변폭과 고정폭 숫자를 마련해 주식 수, 전체 매출액 등 큰 수와 실시간으로 반영되는 수치들에는 고정폭을 활용하고" — 단일 정보에는 가변폭.
- **중립적 형태**: "글자 대신 글이, 형태 대신 내용이 더 잘 보일 수 있도록 과도하게 특징적인 부분은 모두 절제했어요."
- **속공간 확대**: "둥글고 시원한 인상을 주었습니다. 이는 읽기의 피로도를 낮출 수 있게 하는 큰 요인이 됩니다."
- **버티컬 메트릭스**: 기존 서체는 "한글 위치가 시각적으로 중앙에 정렬되어 있지 않고 너무 높거나 낮은 경우가 많았어요" → 한글이 시각적 중앙에 오도록 메트릭 재설계.

> 참고: Toss Product Sans는 **외부 배포 불가(내부 사용 전용)**. MORU는 Noto Sans KR 유지가 맞습니다. 다만 위 원칙 중 "숫자·기호를 본문보다 눈에 띄게", "고정폭 숫자" 두 가지는 폰트 설정으로 흉내 낼 수 있습니다 (Noto Sans KR은 `font-feature-settings: "tnum"` 지원).

### UX 라이팅 원칙

토스 공식 「UI/UX 가이드」(앱인토스 개발자센터)에서 확인한 원칙과 실제 O/X 예시:

| 원칙 | X | O |
|---|---|---|
| **해요체 통일** | — | "모든 문구에 해요체 적용. 상황·맥락 불문." |
| **능동형** | "됐어요" | "했어요" |
| **긍정형** | "안 돼요", "없어요" | "~하면 할 수 있어요", "있어요" |
| **표기 통일** | "되어요" | "돼요" (모바일 좁은 화면 기준) |
| **다이얼로그 좌측 버튼** | "취소" (작업이 취소된다고 오해) | "닫기" |
| **한자어/명사 조합 풀어쓰기** | "선택 권장" 류 명사 조합 | "선택할 수 있어요" |
| **캐주얼한 경어** | "~하시겠어요", 동사의 '~시' | '~시' 제거, "에게"로 통일 |
| **'-하기' 남용 금지** | "확인하기", "등록하기" 무분별 사용 | 버튼만 봐도 다음 행동이 예측되는 동사 |

**구체성 원칙 (앱 상세 설명 O/X — 원문 인용)**
- (X) `필터를 제공해요.`
  (O) `해외 장학금, 거주 지역, 가구원 정보를 기반으로 필터를 제공해요.`
- (X) `알림을 신청하면 나에게 딱 맞는 장학금 정보를 알려줘요.`
  (O) `알림을 신청하면 거주 지역과 가구원 정보를 기반으로, 나에게 딱 맞는 장학금의 금액과 접수 기한을 알림으로 알려줘요.`

**푸시/알림 문구 O/X (원문 인용)**
- (X) `[떡볶이로?] 토스에서 MBTI 심리테스트 진단하세요.`
  (O) `[퍼즐 도전] 토스에서 퍼즐 맞추고 포인트 받아 가세요.`
- (X) `[문장 카드로] 토스에서 39종 카드 골라보세요.`
  (O) `[문장 카드] 토스에서 명언 고르고 원하는 디자인 선택해요.`

**금지 표현 (원문 인용)**: `"지금 바로!"`, `"초특가!"`, `"놓치면 후회해요"`

> 반론도 함께 참고할 것: 디지털인사이트 「UX 라이팅, 무작정 토스처럼 말 걸지 마세요」 — 토스의 라이팅은 "친구처럼 들리게"가 목적이 아니라 간결성·유용성·일관성을 브랜드에 최적화한 결과이므로, 말투만 베끼면 안 된다는 비평.

### 컴포넌트 규칙

**⚠ 아래 수치는 3자 정리 사이트(oh-my-design.kr)의 값입니다. 토스 1차 공식 문서에서 재확인하지 못했으므로 "참고값"으로만 쓰세요.**

- 버튼 (TDS Mobile, XLarge): 높이 **56px**, 패딩 `0 20px`, radius **16px**, 텍스트 **17px / weight 600**, 배경 `#3182f6` / 텍스트 `#ffffff`
  - 상태: fill / weak, loading, disabled, pressed, keyboard focus
- 마케팅 버튼: weak CTA 높이 40px / radius 7px, 다크 버튼 높이 46px / `rgba(0,12,30,0.8)`
- 스페이싱: xs 4 / sm 6 / md 8 / lg 16 / xl 24 / xxl 32
- 웹 타이포 (마케팅): H1 36/700/54, H2 30/600/45, H3 24/600/36, H4 22/600/33, Body 16/400/24, Body Small 14/400/21

> 버튼 높이 56 + 텍스트 17px는 위 TDS 토큰의 `Typography 5 (17/25.5)`와 정확히 맞물립니다. 상호 검증되는 부분.

### 컬러 팔레트

**1차 출처 (TDS React Native 공식 Colors 문서)** — 팔레트 양 끝값만 문서에서 확인:
- Grey: `#f9fafb` (grey50) → `#191f28` (grey900)
- Blue: `#e8f3ff` (blue50) → `#194aa6` (blue900)
- **Red (alert/error): `#ffeeee` (red50) → `#a51926` (red900)**
- 그 외 계열: Orange, Yellow, Green, Teal, Purple (각각 50~900 스텝)
- Grey Opacity: 2%~91% 반투명 변형 (오버레이용)
- `colors.background` = `#FFFFFF`, `colors.greyBackground`, `colors.layeredBackground`, `colors.floatedBackground`
- 사용법: `import { colors } from '@toss/tds-react-native'` → `backgroundColor: colors.blue500`

**3자 정리 참고값 (재확인 못 함)**: Primary `#3182f6` / Primary hover `#2272eb` / Danger `#e42939` / Foreground `#191f28` / Body `#4e5968` / Muted `#8b95a1` / Surface `#f2f4f6` / Border `#e5e8eb` / Weak bg `#e8f3ff` / Weak fg `#1b64da`

**경고·주의 색 사용 원칙**
- TDS는 **Red 계열을 alert/error 전용**으로 명명(naming)해 분리해 둠. 즉 "경고색은 팔레트에서 별도 축으로 존재하되, 본문 계층(Grey)과 액션 계층(Blue)을 침범하지 않음."
- 토스 UI/UX 가이드는 **경고색 hex를 직접 명시하지 않음(확인 실패)**. 대신 명시된 원칙은:
  - "다크/라이트 모드 모두에서 구분 가능한 색감 필수"
  - 색 대비 기준 미충족 시 자동 보정
  - **부정적 커뮤니케이션 최소화 — "없어요" 대신 "할 수 있어요"**
- 즉 토스는 **색으로 겁주기보다 문구를 긍정형으로 바꾸는 쪽**을 택함. MORU 방향과 정확히 일치.

### 훔칠 것 / 피할 것

**훔칠 것**
1. **본문 행간 1.5 고정 룰.** 11~18px 구간 전부 lineHeight = fontSize × 1.5. MORU 본문·기록 리스트에 그대로 이식 가능. (제목은 20px 이상부터 1.45 → 1.33으로 조이기)
2. **긍정형 강제 + "취소" 금지.** MORU는 "위험/이상/문제" 같은 판정 어휘를 아예 어휘집에서 제거하고, 다이얼로그 좌측은 "닫기"로 통일.
3. **구체성 원칙.** "패턴을 보여드려요" (X) → "최근 3주 중 유제품을 먹은 날 9일, 그중 불편했던 날 6일이에요" (O). 토스의 장학금 예시와 같은 구조.
4. **숫자에 고정폭(tabular) 적용.** 기록 리스트·날짜·횟수가 세로로 흔들리지 않게. Noto Sans KR + `font-variant-numeric: tabular-nums`.

**피할 것**
1. **토스의 자신감 있는 단정 톤.** 토스는 "이만큼 아꼈어요" 같은 확정 정보를 다루지만 MORU의 데이터는 관찰치일 뿐. 같은 어조를 쓰면 판정이 됨.
2. **Blue #3182f6 계열 액센트.** MORU 세이지 그린 #7E9F6E와 충돌하고 "금융 앱" 인상을 줌. 토스에서 가져올 것은 *구조와 문법*이지 *색*이 아님.
3. **56px 대형 CTA를 매 화면에 두는 습관.** 토스는 전환이 목적이라 강한 CTA가 정당하지만, MORU는 "기록 안 해도 괜찮은" 앱이라 강한 CTA가 압박으로 읽힘.

## 2. 카카오헬스케어 파스타 (PASTA)

### 개요
Dexcom G7 / 케어센스 에어 CGM(연속혈당측정기)과 SDK로 직접 연동해 **5분 단위 실시간 혈당**을 보여주는 AI 건강관리 앱. 2024년 2월 출시.

### 화면 구조

- **다이어리 탭 (홈에 해당)**
  - 상단: **실시간 혈당 그래프 영역** — 현재 수치(숫자) + 추세 화살표 + 시계열 그래프
  - 하단: **생활 습관 기록** (식사 / 운동 / 수면 / 체중 / 약)
  - **그래프 영역과 습관 기록 사이에 AI가 콘텐츠를 추천** — 사용자가 선택한 질환 유무·상태에 따라 다른 콘텐츠가 들어감
- **기록 탭** — 푸드샷 등 입력
- **리포트 탭** — CGM 착용 기간 데이터를 분석해 혈당 변동성 / 혈당관리지표(GMI) / 목표 범위 내 비율(TIR) / 평균 혈당 / 혈당 하이라이트를 요약 제시. **"잘한 점"과 "아쉬운 점"을 구분해 보여줌**
- **친구 공유** — 가족·의료진과 데이터 공유

### 혈당 수치를 어떻게 표현하나 ← MORU 핵심 참고 지점

공식 FAQ 「다이어리 탭에 나오는 숫자와 색, 화살표의 의미가 궁금해요」 기준:

1. **숫자** — 현재 혈당값을 큰 숫자로 직접 노출.
2. **색** — "혈당 수치가 어느 범위에 위치하는지에 따라 그래프 색상이 달라집니다." 색은 **절대값이 아니라 "내가 설정한 진단유형별 목표 범위"를 기준**으로 결정됨. 목표 범위에서 얼마나 벗어났는지를 직관적으로 보여주는 용도.
3. **화살표** — 숫자 옆 화살표의 **모양과 방향**으로 변화 추세 표시. "향후 30분 이내에 혈당이 어떤 추세로 변동할지 예측하는 데 도움이 됩니다."

> **핵심 설계 원칙 3가지 (MORU가 그대로 가져갈 수 있음)**
> - **색은 절대 기준이 아니라 개인 목표 범위 대비 상대 위치**를 나타낸다.
> - **숫자 + 색 + 방향**을 분리해 3개 채널로 정보를 나눔. 색 하나에 모든 의미를 싣지 않음.
> - **현재 값보다 "추세"를 함께 준다.** 점 하나가 아니라 흐름.

**색상 hex: 확인 실패.** FAQ 페이지의 색상-범위 매핑표가 이미지 파일로만 제공되어 텍스트로 추출 불가. 일반적으로 CGM 앱은 목표 범위 내=회색/녹색, 고혈당=노랑/주황, 저혈당=빨강을 쓰지만 **파스타의 실제 hex는 확인하지 못했습니다.**

### 경고·주의 상황의 문구와 색

- 저혈당 시: **"당 섭취를 제안"**
- 고혈당 위험 시: **"'걷기'와 같은 가벼운 운동을 추천"** / "1,000보 걷기 등의 가벼운 운동을 추천"
- 즉 **"위험합니다"라고 말하지 않고 곧바로 할 수 있는 행동을 제안**하는 구조. 판정 대신 다음 한 걸음.
- 경고 색 hex: **확인 실패.**

### 식사 기록 입력 방식 — 푸드샷

- **사진 한 장이 입력의 전부.** 공식 문구: "사진 한 장으로 내 일상을 자연스럽게 기록할 수 있어요. AI가 음식, 체중계, 혈당측정기 사진 속 정보를 자동으로 인식하고 분석"
- 카카오 원문: "음식을 먹기 전, '파스타'에 탑재된 '푸드샷'을 통해 사진을 찍어 올리면 음식의 종류, 영양 성분, 열량 등이 자동으로 앱에 기록된다"

### 훔칠 것 / 피할 것

**훔칠 것**
1. **"목표 범위 대비 상대 위치"로 색을 정하는 방식.** MORU는 절대 기준(이 음식=위험)이 아니라 **"내 평소 대비"** 로 표현하면 판정을 피하면서도 정보를 줄 수 있음.
2. **숫자·색·방향 3채널 분리.** MORU 패턴 화면에서 "빈도(숫자) + 흐름(방향) + 강조도(색)"를 따로 두면 하나가 과하게 읽히는 걸 막음.
3. **경고 대신 곧바로 행동 제안.** "저혈당 → 당 섭취를 제안" 구조를 그대로 번역: "속이 불편했던 날이 이어졌어요 → 오늘은 따뜻한 식사를 먼저 해볼까요" 식.
4. **사진 한 장 = 입력 완료.** MORU의 최소 입력 목표에 가장 직접적인 벤치마크. 텍스트 입력을 0으로 만드는 방향.
5. **"가르치려 들지 않고 친구처럼"** 을 명시적 톤 원칙 문장으로 채택.

**피할 것**
1. **포인트·챌린지·리워드 시스템.** 파스타는 파스타몰 포인트 리워드를 붙였지만, MORU는 스트릭·점수 금지 원칙과 정면 충돌. 절대 가져오지 말 것.
2. **GMI / TIR 같은 임상 지표 요약.** 수치화된 종합 지표는 사실상 "점수"로 읽힘. MORU에는 종합 지표 자체를 만들지 말 것.
3. **"잘한 점 / 아쉬운 점" 이분법 리포트.** '아쉬운 점'은 평가어. MORU는 "눈에 띈 것 / 아직 알 수 없는 것"처럼 판정이 아닌 축으로 바꿔야 함.
4. **CGM 같은 실시간 연속 수치의 UI 문법을 그대로 이식하기.** 혈당은 초 단위로 변하는 객관 수치지만 IBS 불편감은 주관·저빈도. 같은 라인 그래프 문법을 쓰면 정밀도를 과장하게 됨.

## 3. Finch — 자기돌봄 앱

### 개요
Finch Care Public Benefit Corporation. 가상 반려새(Finch)를 키우는 자기돌봄 앱. App Store 4.9/5 (약 74만 평가), Apple Editors' Choice. 온보딩 18단계.

### 최소 입력을 어떻게 설계했나

1. **체크 하나 = 완료.** 목표(goal)를 체크박스로 완료하면 그 즉시 새의 에너지바가 채워짐. 추가 입력 없음.
2. **기분 체크인은 5단계 얼굴.** "How are you feeling right now?" 질문에 **1~5 얼굴 표정 스케일**(찡그림 → 미소)로 답함. 숫자 입력·텍스트 입력 없음.
3. **목표를 사용자가 직접 정함.** 프리셋 프로그램을 따르는 게 아니라 자기 목표를 스스로 정의. 실제로 등록되는 목표가 극단적으로 작음 — 예: "stand up for 10 seconds"(10초 서 있기), "Plan out my meals for the next day".
4. **온보딩의 커스터마이징 퀴즈는 "large, tappable cards"** 로 구성 — 타이핑 없이 탭만으로 데이터 수집(low-friction).

### 진전(progress)을 점수 없이 표현하는 방식 ← 핵심

- **에너지바 = 목표 완료도.** 대시보드에서 에너지바가 목표 완료와 직접 연동. 점수가 아니라 "새가 나갈 수 있는 상태인지"를 나타냄.
- **새의 성장과 모험이 진전 그 자체.** 완료 → 새가 에너지를 얻음 → 새가 탐험을 나감 → 돌아와서 여행담을 들려줌. **진전이 숫자가 아니라 "이야기"로 반환됨.**
- **레인보우 스톤(rainbow stones)** — 앱 내 재화. 꾸미기용이지 실력 점수가 아님.
- **스트릭 없음 / 벌칙 없음.** 리뷰들이 공통으로 지적하는 지점: 전통 습관 앱은 스트릭이 끊기면 죄책감을 만들지만, Finch는 **"자기를 돌보면 새가 이득을 본다"** 는 구조로 뒤집음. 쉬는 날에 대한 페널티가 없고, 돌아오면 반가워하는 동료만 있음.
- **패턴은 나중에 조용히.** 하루 중 여러 번의 기분 체크인이 쌓이면 **insights 뷰에서 시간이 지난 뒤 패턴을 보여줌.** 매일 결과를 들이대지 않음.

### 톤앤매너·일러스트

- 파스텔·둥근 형태의 2D 일러스트, 의인화된 새 캐릭터. 온보딩에서 알 색상 선택 → 이름 → 대명사(pronoun) → 성격 특성 선택.
- **버튼: 화면 하단 고정 녹색 버튼.** 텍스트는 바뀌지만 "크기와 색상은 대체로 동일"하게 유지 → 사용자가 다음 행동 위치를 학습하게 함. (MORU 세이지 그린과 톤이 가장 가까운 레퍼런스)
- 톤: 판단 없는 지지. UX 티어다운 인용 — 앱이 "정서적 돌봄을 판단 없이" 제공하는 느낌, "일일 의도, 빠른 감사 노트, 맞춤형 긍정 문구가 가볍지만 의미 있음".
- 목표 달성 시 컨페티 애니메이션 (약 04:12 지점).

### 사용자가 "부담 없다"고 느끼는 이유 (리뷰 종합)

1. **감정적 앵커링** — 자기돌봄을 "나를 위한 의무"가 아니라 "새를 위한 돌봄"으로 치환. 자기 자신에게 가혹한 사람도 남(새)에게는 관대함.
2. **실패 상태가 존재하지 않음** — 스트릭·감점·경고가 없음. 안 한 날은 그냥 아무 일도 일어나지 않음.
3. **목표 단위가 우스울 만큼 작음** — "10초 서 있기"가 유효한 목표로 인정됨.
4. **결과가 즉시, 그리고 귀엽게 돌아옴** — 에너지바 + 컨페티 + 새의 반응.

### 실제 UI 문구 (원문 + 해석)
1. "Start mornings with quick mood checks and energize your pet to go exploring!" — 아침은 빠른 기분 체크로 시작하고, 반려새에게 에너지를 줘서 탐험을 보내세요! (App Store 설명)
2. "How are you feeling right now?" — 지금 기분이 어때요? (기분 체크인 헤더)
3. "Have you used Finch before?" — Finch를 써본 적 있나요? (온보딩 첫 분기)
4. "stand up for 10 seconds" — 10초 동안 서 있기 (기본 제공 목표 예시)
5. "Plan out my meals for the next day" — 내일 먹을 것 미리 정해두기 (목표 예시)
6. 컨셉 문장: "taking care of yourself is taking care of your pet" — 나를 돌보는 게 곧 내 반려새를 돌보는 것

### 컬러 팔레트
- **정확한 hex: 확인 실패.** Finch는 공개 디자인 시스템이나 브랜드 가이드를 공개하지 않았고, 리뷰·비평문에서도 hex를 명시한 자료를 찾지 못했습니다.
- 문헌으로 확인 가능한 것: **CTA 버튼이 녹색(green)**, 전반적으로 파스텔 톤. 그 이상은 추측이 되므로 적지 않습니다.
- 색을 정확히 뽑으려면 App Store 스크린샷에서 직접 스포이드 추출 필요.

### 훔칠 것 / 피할 것

**훔칠 것**
1. **"실패 상태를 만들지 않는다"는 설계 원칙.** 안 한 날 = 아무 일도 없는 날. MORU에서 미기록일을 회색 빈칸이나 "놓친 날"로 표시하지 말 것.
2. **진전을 숫자 대신 서술로 반환.** Finch의 "새가 다녀온 이야기" ↔ MORU의 "이번 주에 눈에 띈 것 하나". 성취를 스칼라가 아니라 문장으로.
3. **5단계 얼굴 스케일.** IBS 불편감 입력에 그대로 적용 가능. 숫자 없이 표정만. 탭 한 번.
4. **하단 고정 CTA의 색·크기를 절대 바꾸지 않기.** 문구만 바꿈 → 학습 부담 제거.
5. **극단적으로 작은 최소 단위 인정.** "오늘은 한 끼만 기록해도 충분해요" 같은 명시적 허용.

**피할 것**
1. **게이미피케이션 전체 레이어** — 레인보우 스톤, 상점, 수집, 퀘스트, 컨페티. MORU의 "점수·게이지·스트릭 금지" 원칙과 충돌. 특히 **에너지바는 사실상 게이지**이므로 그대로 가져오면 안 됨 (개념은 훔치되 시각적으로 바 형태는 피할 것).
2. **18단계 온보딩.** Finch는 감정적 애착을 만드느라 길지만, MORU는 "당장 오늘 하나 기록"이 목적. 3~5단계로.
3. **화면 밀도.** Pratt 디자인 비평이 지적한 실제 문제 — "많은 페이지의 UI가 어수선(cluttered)"하며 progressive disclosure로 다시 설계해야 한다는 제안. MORU는 이 함정을 처음부터 피할 것.
4. **캐릭터 의존.** 캐릭터가 있으면 "캐릭터를 실망시키는 것" 자체가 새로운 압박이 될 수 있음. MORU는 캐릭터 없이 문장으로 같은 온기를 만들어야 함.

## 4. Bearable — 증상·기분 트래커

### 개요
90만+ 사용자. 정신건강, 기분장애, 통증, 피로, ADHD 등 수백 가지 건강 이슈 추적. App Store 4.7/5. 무료 + 프리미엄(£4.49~£49.99).

### 입력 항목이 많은데 어떻게 지치지 않게 만들었나 ← MORU 직결

1. **타이핑 제로 원칙.** 공식 문구: **"Enter symptoms with just a few taps. No typing needed"** (몇 번의 탭만으로 증상 입력. 타이핑 불필요) / **"Record your mood, energy, sleep, symptoms, habits, medication, and bowel movements in seconds"** (기분·에너지·수면·증상·습관·약·배변을 몇 초 만에 기록)
2. **척도 폭을 의도적으로 좁힘.** 이게 가장 중요한 설계 결정. **증상은 0~4 (5단계)** 를 씀. 그 이유를 공식적으로 밝힘:
   > 여러 질환에 각각 여러 증상을 가진 사람에게 0~10 척도를 반복해서 보여주는 것은 압도적(overwhelming)이 되기 때문.
3. **사용자가 추적 항목을 직접 고름.** 커스텀 증상·증상 그룹 생성 가능. 안 쓰는 항목은 애초에 화면에 없음.
4. **자동 수집으로 입력을 줄임.** Apple Health 동기화 (심박수·혈압·체중·걸음 수).

### 증상 강도 입력 UI — 척도 체계 (공식 문서 기준)

| 영역 | 척도 | 라벨 |
|---|---|---|
| **Symptoms** | **0~4 (5단계)** | **none / mild / moderate / severe / unbearable** |
| Mood | 1~10 | (라벨 확인 실패) |
| Energy | 1~10 | (라벨 확인 실패) |
| Sleep Quality | 1~5 | (라벨 확인 실패) |
| Custom Ratings | 1~5 | (라벨 확인 실패) |
| Bowel Movements | 1~7 | **Bristol Stool Chart** (lumpy / smooth / watery 등) |
| Health Measurements | 0~20,000 (사용자 정의 범위) | 단계 라벨 없음 |

- **UI 형태(슬라이더 vs 단계 버튼): 확인 실패.** 공식 문서와 리뷰에서 컨트롤 형태를 명시한 자료를 찾지 못했습니다. 다만 "just a few taps, no typing"이라는 공식 문구로 미루어 **연속 슬라이더가 아니라 이산적 탭 타깃**임은 강하게 시사됨.
- **⭐ IBS 직접 관련**: Bearable은 **Bristol Stool Chart(브리스톨 대변 척도) 1~7단계를 정식 입력 항목으로 내장**하고 있음. MORU가 배변 기록을 다룬다면 이미 검증된 표준 척도.

### 상관관계 리포트를 어떻게 보여주나 ← MORU "패턴 분석" 화면 직결

**용어 설계**
- **"Factor"** = 삶에서 일어나는 습관·사건·행동을 묶는 용어. 공식 정의: "*Factor* is a term that we use to group together habits, events, and actions that happen in your life." 예: 커피 마시기, 출근, 명상, 파트너와 다툼, 야외 활동.
- → **"원인(cause)"이나 "트리거(trigger)"라고 부르지 않고 중립어 "Factor"를 씀.** 이름 단계에서 이미 판정을 회피.

**화면 구조**
- **Insights 탭** → **폰을 가로로 회전**하면 비교 그래프(Comparison Graph)가 나옴
- 하단 드롭다운: "Select Mood, Symptom Score, Individual Symptoms, Sleep Quality, Sleep Quantity, or Energy Levels" (비교할 건강 지표 선택)
- 우측 상단: Factor 선택 → 선택한 Factor가 **그래프 배경에 그라데이션으로** 깔림 (별도 선/막대가 아니라 배경 음영)
- 결과 표현: 해당 Factor가 있던 날이 건강 지표에 **"positive, negative, or neutral impact"** 를 줬는지 판단
- 프리미엄: 각 리포트를 눌러 들어가면 **Factor Effect reports** 제공

**단정하나, 조심스럽게 표현하나 → 명확히 "조심스럽게".** 공식 문서 원문:

> **"Correlations are not causation. Bearable can help you to identify patterns between symptoms and factors. However, it cannot tell you whether that pattern is because the factor caused the change in symptoms."**
> (상관은 인과가 아닙니다. Bearable은 증상과 요인 사이의 **패턴을 발견하도록 도울 수는** 있지만, 그 패턴이 그 요인이 증상 변화를 **일으켰기 때문인지는 알려줄 수 없습니다**.)

> **"Correlations are open to interpretation. It's important to sense check your correlations, if they don't make sense at first gleance, is there anything that might explain this?"**
> (상관관계는 해석의 여지가 있습니다. 결과를 상식적으로 검토하는 게 중요합니다 — 첫눈에 말이 안 된다면, 이걸 설명할 만한 다른 게 있을까요?)

> **"Confounding variables, i.e. a third variable that influences both the supposed cause and the supposed effect."**
> (교란 변수 — 추정 원인과 추정 결과 양쪽에 모두 영향을 주는 제3의 변수)

> **"Reverse relationships, i.e. The factor happens alongside the symptom for other reasons, for example pain medications might be taken on days when you have more pain."**
> (역방향 관계 — 요인이 다른 이유로 증상과 함께 나타나는 경우. 예: 통증약은 통증이 심한 날에 복용됨)

**데이터 임계값 (필요 기록량을 명시)**
- 증상+요인 데이터 **약 7일**이 모이면 요인과 증상 강도 변화 사이의 상관을 보여주기 시작
- **최소 30일**이 있어야 어떤 요인이 증상에 부정적 영향을 줄 수 있는지 판단 가능
- 좋은 비교를 위해: **"Having at least 7 days with, and 7 days without, a single Factor will help."** (한 요인이 있던 날 7일 + 없던 날 7일이 있으면 도움이 됩니다)

> **이게 MORU가 가장 크게 훔칠 지점입니다.** "데이터가 얼마나 모여야 무슨 말을 할 수 있는지"를 사용자에게 먼저 알려주는 것 자체가 판정 회피 장치입니다.

### 실제 UI·문서 문구 (원문 + 해석)
1. "Enter symptoms with just a few taps. No typing needed" — 몇 번의 탭만으로 증상 입력. 타이핑 필요 없어요
2. "Measure symptoms by their severity and frequency" — 증상을 강도와 빈도로 측정하세요
3. "See how symptoms correlate with mood, sleep, and energy levels" — 증상이 기분·수면·에너지와 어떻게 연관되는지 확인하세요
4. "Use symptom reports to spot patterns" — 증상 리포트로 패턴을 발견하세요 ("원인을 찾으세요"가 아님)
5. "Find treatments and activities that make you feel better" — 기분이 나아지게 하는 처치와 활동을 찾아보세요
6. "Correlations are not causation." — 상관은 인과가 아닙니다
7. 척도 라벨: "none / mild / moderate / severe / unbearable"

### 컬러·타이포
- **컬러 hex: 확인 실패.** Bearable은 공개 디자인 시스템·브랜드 가이드가 없고, 공식 문서·리뷰에도 hex 명시가 없습니다. 척도 단계별 색상 매핑도 문서화되어 있지 않습니다.
- **타이포: 확인 실패.** 폰트·크기 규격 공개 자료 없음.
- 문헌으로 확인 가능한 것: "clean and easy UI", "very customizable", **다크모드 지원**. 그 이상은 추측이 되므로 적지 않습니다.
- 색을 정확히 뽑으려면 App Store 스크린샷 스포이드 추출 필요.

### 화면 구조 (텍스트 묘사)
```
[기록 화면]
 각 섹션이 세로로 쌓이고, 섹션마다 이산 단계 탭 타깃
 ┌────────────────────────────┐
 │ Mood        1 ─────── 10   │
 │ Energy      1 ─────── 10   │
 │ Symptoms                   │
 │   두통    [0][1][2][3][4]   │  ← none~unbearable
 │   복부팽만 [0][1][2][3][4]   │
 │ Sleep Quality  1 ── 5      │
 │ Factors  (탭으로 선택)       │
 │   ☐커피 ☐출근 ☐명상 ☐외출   │
 └────────────────────────────┘

[Insights 탭 → 폰 가로 회전]
 ┌──────────────────────────────────────┐
 │  [우상단: Factor 선택 ▾]              │
 │   ░░▒▒▓▓  ← 선택 Factor = 배경 그라데이션 │

 │  [하단 드롭다운: Mood / Symptom Score /│
```

### 훔칠 것 / 피할 것

**훔칠 것**
1. **"Factor"라는 중립 명명.** MORU도 "유발 음식", "트리거", "위험 음식"이 아니라 **"요인" / "함께 기록된 것"** 같은 중립어를 쓸 것. 이름 하나로 판정의 절반이 사라짐.
2. **"상관은 인과가 아닙니다"를 리포트 화면 안에 상시 노출.** 각주로 숨기지 말고 패턴 화면의 고정 문구로.
3. **0~4 / 5단계 척도.** 0~10을 반복 노출하면 압도적이라는 Bearable의 근거 있는 결론. MORU는 5단계 이하로 갈 것. (Finch의 5단계 얼굴과도 일치)
4. **필요 기록량을 먼저 알려주기.** "7일이 모이면 흐름을 볼 수 있어요 / 30일이 모이면 더 또렷해져요" 식. **매일 강요하지 않으면서 왜 기록하는지 설명**하는 유일하게 자연스러운 방법.
5. **선택 요인을 배경 그라데이션으로 깔기.** 두 개의 선을 겹쳐 그리면 "이게 저걸 일으켰다"로 읽히지만, 배경 음영은 "이 시기에 이게 있었다"로만 읽힘. **시각 문법 자체가 인과를 주장하지 않음.** MORU 패턴 화면에 그대로 이식할 것.
6. **Bristol Stool Chart 1~7 내장.** IBS 앱이라면 이미 검증된 표준.

**피할 것**
1. **"Symptom Score" 같은 종합 점수 지표.** Bearable에는 존재하지만 MORU 원칙상 금지. 개별 항목만 두고 합산하지 말 것.
2. **폰을 가로로 돌려야 나오는 핵심 화면.** 발견 가능성이 낮은 명백한 UX 부채. MORU는 세로에서 다 보이게.
3. **입력 항목 무한 확장.** Bearable은 수백 가지를 추적할 수 있는 게 강점이자 이탈 원인. MORU는 **항목 수 상한을 두고**, 늘리는 건 사용자가 명시적으로 요청할 때만.
4. **"negative impact" 같은 가치 판단 라벨.** Bearable도 여기서는 판정어를 씀. MORU는 "불편했던 날이 더 많았어요" 같은 **관찰 서술**로 바꿀 것. positive/negative/neutral 대신 **"함께 나타난 날 N일 / 그렇지 않은 날 M일"** 처럼 숫자만 제시.
5. **프리미엄 뒤에 상관관계 리포트 숨기기.** MORU의 핵심 가치가 패턴 제시라면 무료로.

| 용도 | 크기 | 행간 | 배수 | 근거 |

| 본문 (기본 권장) | 16px | 24px | **1.5** | TDS subTypography 10 |

| 캡션 / 보조 | 13px | 19.5px | **1.5** | TDS Typography 7 |
| 소제목 | 20px | 29px | 1.45 | TDS Typography 4 |
| 화면 제목 | 22px | 31px | 1.41 | TDS Typography 3 |
| 큰 제목 | 26px | 35px | 1.35 | TDS Typography 2 |
| 최상위 제목 | 30px | 40px | 1.33 | TDS Typography 1 |

**규칙 요약**: 18px 이하는 무조건 1.5배. 19px부터 크기가 커질수록 배수를 1.45 → 1.41 → 1.35 → 1.33으로 조인다.

**자간 — 확인 실패.**
- 토스의 실제 letter-spacing 값은 **공개 자료에 없습니다.** TDS 문서에도 fontSize/lineHeight만 있고 letterSpacing 토큰이 없습니다.
- 한글 UI 일반론으로 "본문 16~17pt에 약 -0.3 정도 좁힘", "한글 웹폰트에 -1~-2px" 같은 서술이 있으나 **토스 출처가 아니며 MORU 기준으로 삼을 근거가 부족합니다.**
- **권고**: Noto Sans KR은 본래 자간이 넉넉한 편이라 좁히는 게 일반적이지만, **수치는 실기기에서 눈으로 맞춰 정하고 문서에 "자체 결정값"으로 기록**하세요. 레퍼런스 수치로 위장하지 말 것.

**숫자 처리 (토스 프로덕트 산스 원칙 이식)**
- 기록 리스트·날짜·횟수처럼 세로로 정렬되는 숫자에는 **고정폭(tabular)** — `font-variant-numeric: tabular-nums`
- 문장 속 단일 숫자는 가변폭 기본값
- 퍼센트·화살표 등 기호는 본문보다 **약간 크고 여백을 넓게** (토스가 "아이콘에 가깝게" 처리한 이유)

### 문구 작성 원칙 5개

**1. 판정어를 어휘집에서 삭제하고 관찰어로 대체한다.**
Bearable의 "Factor" 명명 전략. "유발 음식 / 트리거 / 위험 / 나쁜 / 아쉬운 점" 전부 금지. 대신 "함께 기록된 것 / 요인 / 눈에 띈 것".
- (X) 유제품이 증상을 유발할 가능성이 높아요
- (O) 최근 3주 중 유제품을 먹은 날은 9일이었고, 그중 6일에 불편함을 기록하셨어요

**2. 긍정형·능동형·해요체로 통일한다. (토스 규칙 직수입)**
- "됐어요" → "했어요" / "없어요" → "있어요" / "안 돼요" → "~하면 할 수 있어요"
- 다이얼로그 좌측 버튼은 항상 **"닫기"** ("취소"는 작업이 취소된다고 오해됨)
- "되어요" → "돼요" 로 표기 통일

**3. 두루뭉술 대신 무엇을 근거로 말하는지 밝힌다. (토스 구체성 원칙)**
- (X) 패턴을 분석해 드려요
- (O) 최근 21일 기록 중 유제품이 있던 9일과 없던 12일을 비교했어요
- 동시에 **한계도 같이 밝힌다**: "상관은 인과가 아니에요. 다른 이유가 있을 수도 있어요."

**4. 경고 대신 곧바로 할 수 있는 한 걸음을 제안한다. (파스타 방식)**
파스타는 "저혈당입니다"가 아니라 **"당 섭취를 제안"**, "고혈당 위험"이 아니라 **"1,000보 걷기 등 가벼운 운동을 추천"**.
- (X) 최근 증상이 악화되고 있어요
- (O) 이번 주는 불편한 날이 좀 있었네요. 내일은 따뜻한 식사부터 해볼까요?

**5. 기록하지 않은 날에 대해 아무 말도 하지 않는다. (Finch 방식)**
실패 상태를 만들지 않는다. 미기록일에 회색 빈칸, "놓친 날", 알림 재촉을 두지 않는다. 그 대신 **필요 기록량을 미리 설명**해서 자발적 동기를 만든다 (Bearable 방식).
- (O) "7일쯤 모이면 흐름이 보이기 시작해요. 지금은 3일이에요."
- (O) "오늘은 한 끼만 기록해도 충분해요."
- (X) "3일 연속 기록 중이에요!" / "어제 기록을 놓치셨어요"
